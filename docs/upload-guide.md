# 往 Xbox 360 硬盘里传文件

两条路，按你的实际情况选。**能开机就走第一条**，那是 360 自己写盘，不经过任何第三方代码。

---

## 路线 A：FTP（推荐，360 能开机就用这个）

硬盘留在机器里，让 360 自己维护 FAT 表。你只通过网络丢文件，不存在 FAT 链写坏的可能。

### 1. 连线

360 用网线接到和 Mac 同一台路由器上。在 360 的「系统设置 → 网络设置 → 有线网络 → 其他信息」里记下 IP，形如 `192.168.1.42`。

### 2. 在 360 上开 FTP 服务

三种都行，选你手上有的：

| 方式 | 怎么开 | 默认端口 |
|---|---|---|
| **Aurora** | 启动 Aurora → 设置里启用 FTP | 21 |
| **F3 (Freestyle 3)** | 设置 → 网络 → FTP | 21 |
| **XeXMenu 1.2** | U 盘运行，按 **LB** 启动 FTP | 21 |

### 3. Mac 上连

用 Cyberduck（免费）或 FileZilla：

- 协议：FTP
- 主机：`192.168.1.42`（填 360 的 IP）
- 端口：`21`
- 用户名 / 密码：**都留空**（匿名）

### 4. 传到哪里

| 内容 | 目标路径 |
|---|---|
| GOD 游戏包、存档、DLC | `Hdd1:/Content/0000000000000000/` |
| 插件、脚本、Aurora 本体 | `Hdd1:/` |
| 标题更新（TU） | `Hdd1:/Cache/` |

`Hdd1:` 就是你那块 500 GB 数据分区（461 GB 可用）。

### 如果盘上还没有 Aurora

盘上目前只有 Dash Launch，没看到 Aurora / F3。要用 FTP 的话，先把 Aurora 文件夹整体传到 `Hdd1:/Aurora/`，再用 Dash Launch 的 `launch.ini` 把它设成默认面板：

```ini
[Default]
Default = Usb:\Aurora\Aurora.xex
```

更省事的做法：U 盘跑 XeXMenu，按 LB 开 FTP 先把 Aurora 传上去。

## 路线 B：BoxingBuffalo 直接写盘（360 开不了机、或你想在 Mac 上离线操作）

BoxingBuffalo 已经加了写入能力：上传文件、新建文件夹、删除、重命名。全部经过确认对话框，并且失败会自动回滚 FAT 表和目录项。

### 操作步骤

1. 启动 `BoxingBuffalo.app`，左侧选「数据分区」
2. 进到目标目录（比如 `Content / 0000000000000000 / 41560914 / 00007000`）
3. 点工具栏的**锁图标**（或侧栏右下「解锁写入…」）→ 输入 macOS 管理员密码
   - 挂载时那次密码只放开**读**权限；写权限必须单独申请这一次
   - 侧栏底部「只读模式 / 读写模式」和锁的颜色跟随真实句柄，解锁成功后会变绿
4. 点**上传文件**（朝上的箭头），选文件（可多选）
5. 确认对话框会列出：目标目录、每个文件的大小、**因为 FATX 不支持中文名而需要改名的文件**
6. 点**写入**

也可以直接把 Finder 里的文件**拖进文件列表**，或拖到某个文件夹那一行上（会写进那个文件夹）。

### 上传整个文件夹

上传面板现在**可以同时选文件和文件夹**，拖放也支持文件夹。文件夹按原目录结构递归创建，同名目录会合并（重复上传不会生成 `Pack (2)/` 这样的副本），同名文件覆盖。

上传前的确认框会列出每个顶层目录的递归统计（文件数、子目录数、总字节），并提示：

- FATX 只支持 ASCII 文件名：`存档.txt` → `_.txt`；超 42 字节会截断
- 自动跳过 `.DS_Store` 等隐藏文件、符号链接、超过 **4 GB** 的单个文件
- 中文名折叠后可能撞名（`中文.txt` 与 `英文.txt` 都变 `_.txt`），只保留第一个并在提示里说明

保留本地文件的修改时间。失败时回滚仍只覆盖元数据扇区与目录项，新分配的数据簇不包含在回滚缓冲里。

### macOS 上的写权限（重要）

自 Catalina 起，`osascript ... with administrator privileges` 起的进程**改不了 `/dev/rdisk*` 的权限位**（`Operation not permitted`），即使密码正确、即使它确实是 root。BoxingBuffalo 因此改用 `sudo -A` + 图形密码框来改权限位。

如果这一步仍报 `EPERM`，是 TCC 在挡裸设备写入，按顺序处理：

1. 在「终端」里手工执行一次（终端的 TCC 授权会被子进程继承）：

   ```bash
   sudo chmod 666 /dev/rdisk8 /dev/disk8
   ```

2. 回 BoxingBuffalo 再点一次锁——此时设备节点已可写，不会再要密码，直接重挂为读写。
3. 若仍报 `EPERM`：系统设置 → 隐私与安全性 → **完全磁盘访问权限** → 加入 `BoxingBuffalo.app`，退出并重开 BoxingBuffalo（应用是临时签名，每次重新构建后可能需要重新授权）。

诊断全过程写在 `~/Library/Logs/BoxingBuffalo.log`：sudo 是否以 root 执行、chmod 的原始输出、设备节点权限、`open(O_RDWR)` 的 errno。

### 顺带支持的写入操作

| 操作 | 入口 |
|---|---|
| 新建文件夹 | 工具栏「新建文件夹」按钮 / 空白处右键 / `⌘⇧N` |
| 删除 | 选中后按 `⌫` / 右键「删除」 |
| 重命名 | 右键「重命名…」 |

## 写入前必须知道的五件事

**1. FATX 文件名只支持 ASCII，最长 42 字节。**
中文名会被自动改成 `_`。想要可读的名字，先在 Finder 里改成英文再传。控制台也不认中文文件名，这不是 BoxingBuffalo 的限制。

**2. 同名文件直接覆盖，旧簇会被释放。**
不会问你「是否替换」，确认对话框里会写明。

**3. 单文件上限 4 GB（FATX 的 size 字段是 32 位）。**
超过会写入失败。要传大文件得切成 GOD 包。

**4. 真盘写入无法撤销——但失败会自动回滚。**
每次写入前会把**将被修改的 FAT 表扇区和目录项**快照到内存，中途出错自动写回原值。文件数据区不备份（新分配的簇，写坏也不影响已有文件）。如果断电或强制退出，最坏结果是泄漏一段簇（空间少了但文件都在）。

**5. 第一次先在根目录写一个 1 KB 的 txt 试。**
接回 360 用文件管理器看一眼，能正常显示、能打开，再传大文件。这比任何自测都可靠。

## 为什么旧版会报「读取失败 … errno 22: Invalid argument」

裸设备（macOS 与 Windows 一样）只接受**偏移和长度都是整扇区（512 字节）倍数**的传输。实测这块 HM500JI USB 桥：

| 请求 | 结果 |
|---|---|
| `pread(0x130eb0000, 512)` | ✔ 512 字节 |
| `pread(0x130eb0000, 256)` | ✗ EINVAL |
| `pread(0x130eb1008, 1048576)` | ✗ EINVAL |
| `pread(0x130eb0200, 1048576)` | ✔ 1048576 字节 |

原版 CLKsFATXLib 用 `FILE_FLAG_NO_BUFFERING | WRITE_THROUGH` 打开 `\\.\PhysicalDriveN`，所以全库到处是 `DownToNearest200` / `UpToNearest200` / `DownToNearestCluster(0x1000)`：**先把底层流定位到扇区边界、读整块，再在内存里按块内偏移切出需要的字节**（`FATXFileStream.Read`、`GetBlocksOccupied`、`WriteFATChain` 都是这个套路）。

旧版 BoxingBuffalo 只在**写**时做了 4096 字节读-改-写，读仍是裸 `pread`；分配器扫描空闲簇时发出的正是 `pread(fatOffset + 8, 1 MiB)`，偏移不是 512 的倍数，内核直接 EINVAL。现在把「对齐读 + 内存切片」下沉到 `RawBlockSource.read`（`SectorAlignedIO`），所有上层调用（FAT 项、目录项、超级块、magic 探测）统一遵守；全盘 magic 探测的 0x100 也改成 0x200 整扇区。

## 已验证 / 未验证

**已验证**

- 合成镜像 **96 项**检查全过（新增「取消上传回归」：20 MiB 在第 2 个写入窗口中止、目录项未提交、FAT 表与根目录簇逐字节还原；含「连续簇合并大块写」回归：20 MiB / 5120 簇 → 3 次设备写、0 次读-改-写预读）：跨簇写入、重新挂载后逐字节一致、覆盖后旧链释放、删除标记 0xE5 与簇回收、目录满时自动扩簇、中文名拒绝、递归文件夹上传（结构/中文名净化/隐藏项跳过/重复上传合并）、**512 字节扇区对齐读取回归**（非对齐 1 MiB FAT 扫描、碎片读、末尾补零、对齐快路径）
- 真盘只读复验：`fatOffset + 8` 处 1 MiB 非对齐读，三个 FATX 卷全部返回完整 1048576 字节 ✔（旧版在这一步报 errno 22）
- 真实盘几何实测：末尾 7376 簇（115.2 MB）**没有物理介质**（正好等于 FAT 表大小），分配器已按此设上限；第一个空闲簇在 2301245，之后连续 832 MB 可用
- 真盘设备节点已放开写权限（`crw-rw-rw-`），BoxingBuffalo 能以 `O_RDWR` 打开 disk8

**未验证**

- 真盘实际写入后 360 能否识别——需要你第一步那个 1 KB 测试文件
- 拖拽上传的手势没法自动点击验证

## 写入性能：为什么以前比 USB 1.0 还慢，现在快了多少

**根因不是带宽，是每簇一次 IO 的固定延迟。** 原版 CLKsFATXLib 为了兼容 `FILE_FLAG_NO_BUFFERING`，所有设备读写都按扇区取整；BoxingBuffalo 照做之后，写文件时每个 16 KiB 簇都要：

1. `RawBlockSource.write` 先读回整个 16 KiB 块（读-改-写），
2. 再单独下发一次 16 KiB 的 `pwrite`。

HM500JI 的 USB 桥每笔小事务约 6 ms 往返，于是 `16 KiB / 6 ms ≈ 2.7 MB/s` —— 和实测的 2.6 MB/s 完全吻合。10 GiB 游戏因此要 70 分钟。

**两处改动**

| 位置 | 改动 |
|---|---|
| `BlockSource.swift` | 4 KiB 对齐且整块覆盖时**直通 pwrite**，跳过读-改-写；只有 4 字节 FAT 项、64 字节目录项这类部分块才走读-改-写 |
| `FatXWriter.swift` | `addFile(from:)` 按 8 MiB 窗口把**簇号连续的簇合并成一次写**；不连续的段退化成单次对齐簇写（仍跳过预读） |

FAT 元数据本来就是连续批量写（`applyFAT`），不是瓶颈；`WriteJournal` 也只记录元数据而非文件数据。

**真盘空闲区实测**（只写 FAT=0 的空闲簇，不动 FAT / 目录项 / 任何文件）

| 场景 | 速率 |
|---|---|
| 旧路径：逐簇 16 KiB 读-改-写 | 1.36 MB/s |
| 旧 app 实际上传（含缓存等因素） | 2.6 MB/s |
| **新路径：8 MiB 合并写** | **10.38 MB/s** |
| 基准提速 | 7.6×（相对 app 实测约 4×） |

窗口大小对比（`/dev/rdisk8`，各写 32 MiB）：1 MiB → 5.15 MB/s，4 / 8 / 32 MiB → 稳定 10.38 MB/s，说明 8 MiB 已在平台期。`/dev/disk8`（缓冲块设备）只有 1.4 MB/s，**不要换设备节点**。10.37 GiB 游戏预计从约 70 分钟降到约 17 分钟；10.38 MB/s 已是这块 USB2 桥 + 5400 转老盘的上限，再快只能换硬盘盒或固态。

**中断后回收孤儿簇**

强停上传会留下一批「FAT 标成占用、但没有任何目录项引用」的簇，因为目录项是最后才提交的。回收脚本：

```bash
python3 ./scripts/reclaim-orphan-clusters.py            # 只读 dry-run
python3 ./scripts/reclaim-orphan-clusters.py --apply    # 备份 + 清零 + 回读校验
```

默认区间是 2026-11-08 那次中断留下的 `cluster 2376801..2425835`（49,035 簇 / 803.4 MB），可用 `--start/--end` 指定别的。`--apply` 会把原 FAT 字节备份到 `backup/fat-orphans-*.bin` 便于回滚，并复验相邻项未变。脚本幂等：区间已全 0 时直接退出。

## 正常取消上传（别再强杀进程）

上传时状态栏右侧会出现进度条和**「取消」**按钮；新建文件夹、删除、重命名这类短操作不显示按钮（它们本来也来不及取消）。

- 点「取消」后按钮变成「取消中」，**当前 8 MiB 写入窗口先跑完**（约 0.8 秒），再到下一个窗口边界停下。
- 停下时 `FatXWriter` 把本次申请的簇写回空闲，`WriteJournal` 把这次上传碰过的**所有 FAT 扇区与目录项**恢复到上传前状态。
- 因此一次上传是原子的：**连前面已经写完的文件也会被撤销**，原有文件（包括被覆盖的同名文件）不受影响；写进数据区的字节留在空闲簇里，下次分配会覆盖，不会变成孤儿簇。
- 状态栏显示「已取消上传 · 本次写入的目录项与 FAT 已回滚…」，**不会**弹错误框。

自检 96 项里有一项专门验证这条链路：20 MiB 文件在第 2 个进度窗口取消 → 目录项数量不变、FAT 表逐字节等于上传前、根目录簇逐字节等于上传前。

## 签名与「可移除宗卷」授权

`scripts/build-app.sh` 现在会自动用本机的 `Apple Development` 证书签名（找不到才退回 ad-hoc），可用环境变量 `BOXINGBUFFALO_SIGN_IDENTITY` 指定别的身份：

```bash
codesign -dv --verbose=2 ./dist/BoxingBuffalo.app 2>&1 | grep -E "Signature|TeamIdentifier|Authority"
```

原因：ad-hoc 签名的 cdhash 每次重建都变，macOS TCC 把「可移除宗卷」授权绑在这个 hash 上，于是每次重建后启动都会再弹一次「BoxingBuffalo 想访问可移除宗卷上的文件」。开发证书给 app 一个稳定的 designated requirement（bundle id + team + Apple anchor），**授权一次即可，之后重建不再弹**。从 ad-hoc 切到证书签名时会再弹最后一次，点「允许」即可。
